# 参考项目 深度拆解 07：日志与诊断体系

> 三层日志定位"绑不上/起不来/连不上"：App 侧绑定链路（ServiceBootLogger）、
> 引擎侧启动 trace（RemoteBootTrace）、独立 logcat 服务进程、会话日志、导出 ZIP。

---

## 1. 日志分层总览

| 日志 | 文件 | 侧 | 记录内容 |
|---|---|---|---|
| ServiceBootLogger | `{ext}/Maa/debug/service_bind_debug.log` | App | 绑定链路事件（bind→CONNECTING→onConnected→binderDied→timeout） |
| RemoteBootTrace | `{ext}/Maa/debug/service_boot_debug.log` | 引擎 | 引擎进程启动各阶段（CTOR→MAA_LOAD→CTOR_DONE） |
| root 启动 | `{ext}/Maa/debug/root_launch_debug.log` | Root | liblauncher 启动 root 进程的输出 |
| logcat 服务 | `{ext}/Maa/debug/logcat/core|app/` | 独立进程 | 按 pid 抓取引擎/App 的 logcat |
| MaaSessionLogger | `{ext}/Maa/debug/...` | App | 每次任务会话日志 |
| LogExportService | `maa_logs_时间戳.zip` | App | 上述全部打包导出 |

---

## 2. ServiceBootLogger（App 侧绑定链路诊断）

```kotlin
object ServiceBootLogger {
    fun init(context) { debugDir = {ext}/Maa/debug; mkdirs; event("SESSION", "app start pid=...") }
    fun event(stage: String, msg: String = "") {
        // 写 service_bind_debug.log，>512KB 轮转（.1 备份）
    }
}
```

事件点：`BIND` / `CONNECTING` / `CB_ON_CONNECTED` / `BINDER_CONNECTED` /
`CB_ON_ERROR` / `BINDER_DIED` / `CONNECT_TIMEOUT` / `GET_INSTANCE_TIMEOUT` / `STUCK` 等。

**诊断价值**：当服务进程静默死亡、binder 永不回投时，文件停在 CONNECTING 行——直接定位"流程卡在 IPC 边界、服务进程未起来"。

## 3. RemoteBootTrace（引擎侧启动 trace）

```kotlin
object RemoteBootTrace {
    // 路径自行推导：/storage/emulated/0/Android/data/{pkg}/files/Maa/debug/service_boot_debug.log
    // （不用 FakeContext.getExternalFilesDir——那会解析到 com.android.shell 的目录）
    fun mark(stage: String, msg: String = "") {
        // 写 service_boot_debug.log + 同时进 logcat/root stderr
    }
}
```

标记点：`CTOR_START` → `MAA_LOAD_BEGIN` → `MAA_LOAD_OK/FAIL` → `CTOR_BEFORE_MAA_SERVICE` → `CTOR_AFTER_MAA_SERVICE` → `CTOR_DONE`。

**为什么自己推导路径**：卡死发生在构造阶段（同步加载 libMaaCore.so），此时进程既无 Context 也拿不到 App 传来的 userDir；用 `Environment.getExternalStorageDirectory() + Android/data/{pkg}/files/...` 自行推导出与 App `getExternalFilesDir` 相同的路径（shell uid 可写）。

## 4. LogcatServiceManager + LogcatCaptureServiceImpl（独立抓 logcat）

App 进程 logcat 权限不足（抓不到引擎进程日志），所以再起一个 **logcat 服务进程**：

```kotlin
object LogcatServiceManager {
    fun bind() {
        when (RemoteAccessCoordinator.configuredBackend()) {
            SHIZUKU -> bindViaShizuku()   // 同主服务：随机 tag + 递增 version + 独立 connection
            ROOT    -> bindViaRoot()      // liblauncher + token + ContentProvider 回传
        }
    }
    suspend fun startCapture(appPid, servicePid, userDir) {
        withTimeout(10_000) { _service.first { it != null } }?.startCapture(...)
    }
}
```

`LogcatCaptureServiceImpl`（logcat 进程）：

```kotlin
override fun startCapture(appPid, servicePid, userDir) {
    // 对每个 pid 起 logcat 子进程：logcat -T 10 --pid=<pid>，输出重定向到
    //   {userDir}/debug/logcat/core/logcat_时间戳.log   （引擎进程）
    //   {userDir}/debug/logcat/app/logcat_时间戳.log    （App 进程）
    // 自带看门狗：目标 pid 消失 → 停对应 logcat 子进程
}
```

- **按 pid 过滤**（`--pid=`），只抓本应用与引擎的日志，不污染；
- 只在 debugMode 下启动（MaaResourceLoader.load 里触发）。

## 5. MaaSessionLogger（会话日志）

- `startSession(taskTypes)`：时间戳 + 任务清单
- `appendAndWait(msg, level)`：写内存 + 磁盘（等待落盘）
- `completeSessionAndWait(status, msg)` / `endSession(status)`：收尾
- 供 UI 展示（logs StateFlow）+ 导出

## 7. CrashHandler（App 崩溃兜底）

- 应用启动时注册；记录未捕获异常到日志文件，便于导出排查。

---

## 8. 给复现者的要点清单

1. 三层诊断：App 绑定链路（service_bind）＋引擎启动（service_boot）＋root 启动（root_launch）。
2. RemoteBootTrace 路径自行推导（不用 FakeContext 的 getExternalFilesDir）。
3. 独立 logcat 服务进程，按 pid 过滤抓取引擎/App 日志；目标 pid 消失自动停。
4. 日志轮转（ServiceBootLogger 512KB / RemoteBootTrace 256KB）。
5. 导出为 ZIP（FileProvider 分享 / SAF 写入），debugMode 附 getprop。
6. 会话日志贯穿任务全生命周期，UI 实时可见。
