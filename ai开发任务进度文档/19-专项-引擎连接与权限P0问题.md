## 🔴 P0-A：手动任务与定时任务"双引擎进程"并发（架构级）

**位置**：`MainActivity.bindRemoteEngine()` 与 `MaaEngineService.ensureRemoteConnected()`
各自 `Shizuku.bindUserService(...)`，各自维护 `remoteBound/remoteService`。

**问题**：
1. 用户手动跑任务的同时，定时任务触发 → MaaEngineService 又绑一个引擎（我改的随机 tag 使两者 **key 必然不同** → 服务端会起 **两个 remote_engine 进程**）。
2. 两个引擎进程**都创建虚拟屏、都加载 MaaCore、都注入触摸** → 虚拟屏/识别/触摸互相抢 → 黑屏、识别错乱、任务互相覆盖。
3. 停止一个引擎会误杀另一个（destroy 按进程）。

**正确做法**：单一 `RemoteServiceManager` 状态机 + `useRemoteService{}` 统一入口，**全 App 只有一份绑定**。

**改造**（P0-6 的落地点）：
- 把绑定收敛到单例（`object RemoteEngineConnector`），MainActivity / MaaEngineService / RootDaemon 全走它；
- 已绑定则复用（`getInstanceOrNull()`），未绑定才 bind；
- 同一时刻只有一个 `activeBinding`（新连接替换旧，旧回调按 `activeBinding?.connection === this` 丢弃）。

**验证**：手动任务运行中触发定时任务 → 不新增引擎进程（`ps -A | grep remote_engine` 只有 1 个）。

## 🔴 P0-B：Shizuku root 模式误切 Root 模式 → App 无 su 则死路

**位置**：`MainActivity.bindRemoteEngine()` 绑定失败分支：

```kotlin
val shizukuRoot = suid == 0                       // Shizuku 服务器是 root
if (shizukuRoot || rootOk) {
    // ⚠ 若 Shizuku root 但 App 无 su：切 Root 模式后必然失败
    SettingsRepository.setRunMode(RUN_MODE_ROOT)
    bindRemoteEngine()   // → RootRemoteServiceConnector 用 App 侧 su → 无 su → 引擎起不来
}
```

**问题**：
- `RootManager.isRootAvailable()` 只查 PATH 里的 su；**Shizuku root 不代表 App 有 su**（用户设备正是：shizuku_server root、App 无 root）。
- 于是：Shizuku 绑定超时（如服务端 record 卡死）→ 检测到 shizukuRoot=true → 切 Root 模式 → App 无 su → Root 引擎也起不来 → **两条路都死，用户无解**。
- 而且 `setRunMode(ROOT)` 把用户设置改了，之后永远走 Root 模式（更糟）。

**改造**：
```kotlin
if (rootOk) {                       // 只有 App 真能 su 才切 Root
    ...切 Root 模式重试...
} else if (shizukuRoot) {
    // Shizuku root 但 App 无 su：继续用 Shizuku（UserService 以 root 运行），不切模式
    addLog("Shizuku 以 root 运行：重启 Shizuku 后重试；或设置页手动重绑")
    cleanupStaleShizukuBinding()    // 清服务端 record 后重试一轮
    delay(3_000); bindRemoteEngine()
} else { ...提示无 root 可操作方案... }
```

**验证**：Shizuku root + App 无 su 的机器上，绑定失败后不切 Root 模式、设置不被动改。

## 🔴 P0-C：Shizuku root 模式（引擎 uid=0）下能力受限风险

**位置**：引擎进程由 Shizuku root 启动时 `uid=0`（非 shell 2000）。

**问题**（uid0 ≠ shell 的差异）：
1. **启动游戏**：`ActivityManager.startActivity` 依赖 shell 的 BAL 豁免；uid0 可能被 SELinux/BAL 拦截 → **游戏起不来 → 虚拟屏黑屏**（这可能是你"游戏启动几秒停止"的另一层原因，如果当时 Shizuku 是 root）。
2. **触摸注入**：`InputManager.injectInputEvent` 依赖 `INJECT_EVENTS`（shell 有，root 走 cap 通常也行，但 SELinux domain 可能拦）。
3. **虚拟屏创建**：root 身份创建 virtual display 在部分 ROM 受限（火影已有提示文案，说明踩过）。
4. **引擎 init 降权/提权**：uid0 会执行 setresuid 降权发广播再提权——正确，但 shell 模式不该执行（S-1）。

**正确做法**：`failVirtualDisplayStart()` 检测 `shizukuAsRoot` → 明确提示"Shizuku 以 root 运行，虚拟屏可能受限，**改用设置页 ROOT 模式**"（注意：正确是提示用户切 Root，因为 正确的 Root 模式用 liblauncher root 进程，与 Shizuku root 进程的 SELinux domain 不同）。

**改造**：
1. 引擎 init 增加 `Ln.w("引擎 uid=%d，%s", uid, if (uid==0) "root（非 shell，能力可能受限）" else "shell")`。
2. 虚拟屏/游戏启动失败时，若 `Process.myUid()==0` 且非 Root 模式，提示用户切到 **Shizuku adb/shell 模式**（对无 root 设备最稳）。
3. 引擎侧 `startApp` 失败时优先走 `am start --display`（已有 fallback），并记录失败原因供诊断。

**验证**：Shizuku root 设备跑任务，若游戏启动失败，日志明确提示"root 身份启动游戏受限，建议 Shizuku 切 adb/shell 模式"。

## 🔴 P0-D：公共目录写入权限（导出日志/截图到 /storage/emulated/0）

**位置**：`LogExporter.targetDir`（/storage/emulated/0/MaaFw日志）；截图导出等。

**问题**：
- Manifest 声明了 `MANAGE_EXTERNAL_STORAGE`，但 **Android11+ 必须运行时申请"所有文件访问权限"**（`Settings.ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION`）。
- 火影 `hasStorageAccess()` 若未在导出前强制校验/引导授权，写 `/storage/emulated/0/MaaFw日志` 会抛 EACCES → **导出日志失败/崩溃**（历史上 logcat 曾见 `EACCES`）。
- 引擎进程（shell uid）写外部存储不受 scoped storage 限制（shell 豁免）——但 App 侧写会受限。

**改造**：
1. 导出前校验 `Environment.isExternalStorageManager()`，未授权 → 弹窗引导跳转授权页（`ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION`）。
2. 无授权时**兜底导出到 App 外部私有目录** `{ext}/files/...`（App 可写），提示用户。
3. 引擎侧写文件（截图等）统一走 userDir（外部私有目录），不依赖公共目录。

**验证**：未授予"所有文件访问"时点导出 → 不崩溃，导到私有目录并提示；授予后导到公共目录。

## 🟠 P1 补充（连接/权限相关）

### P1-X1 引擎侧统一用 FakeContext
- 现状：`RemoteEngineServiceImpl` 主 context 是 Shizuku 传入（app 包名、uid shell 不匹配）；FakeContext 只用于 ActivityUtils 等局部。
- 建议：引擎侧系统服务/包名相关调用统一走 `FakeContext.get()`（如 `getPackageManager`、`getSystemService`），规避 UID/PKG 校验。

### P1-X2 logcat 读取（READ_LOGS）
- App 无 READ_LOGS；logcat 导出必须走引擎（shell）或独立 logcat 服务（P1-2）。现状 captureLogcat 偶发空（43 字节）——按 pid 过滤落盘解决。

### P1-X3 通知权限 → 定时任务前台服务
- `MaaEngineService.onStartCommand` 检查通知权限，未授权则 stopSelf → **定时任务静默失效**。
- 建议：未授权时仍尝试 startForeground（Android13+ 无通知权限 FGS 可启动但通知不可见），或给出"定时任务需通知权限"提示。

### P1-X4 Shizuku 授权状态前置
- 绑定前 `checkSelfPermission` 未授权 → requestPermission；若 Shizuku 未运行 → 直接提示。建议加 S-3 一键引导。

## 📋 汇总：引擎连接+权限 P0 行动清单

| 编号 | 问题 | 改动 | 优先级 |
|---|---|---|---|
| P0-A | 双入口双引擎进程 | 绑定收敛单例（RemoteEngineConnector） | 高 |
| P0-B | Shizuku root 误切 Root 死路 | 仅 `rootOk` 才切 Root；shizukuRoot 走 Shizuku 重试 | 高 |
| P0-C | Shizuku root 能力受限 | uid 检测 + 明确提示 + am fallback | 高 |
| P0-D | 公共目录写权限 | MANAGE_EXTERNAL_STORAGE 运行时授权 + 私有目录兜底 | 中 |
| P1-X1~X4 | FakeContext 统一 / logcat / 通知权限 / Shizuku 引导 | 分批 | 中 |

> 优先级：**P0-A（双引擎）与 P0-B（Root 死路）会直接导致"任务无法运行/绑定反复失败"**，
> 建议先做；P0-C 与你的"游戏启动几秒停止"直接相关（若 Shizuku 处于 root 模式）。
